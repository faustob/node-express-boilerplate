**Auto-fixed during review (4):**
- qr-not-a-noop (`src/config/tracing.js`): The meter and its instruments (httpServerRequestDuration, httpServerRequestOutcomes, authOperations) are created at module load in the SAME file that calls sdk.start(), but if sdk.start() throws and is swallowed, the SDK never registers. More critically, meter/instruments are created synchronously right after sdk.start(); OTel-JS has no metrics proxy, so if the global MeterProvider is not yet installed at the moment metrics.getMeter() runs, the instruments bind to a NoopMeter that never rebinds. Because these instruments are captured once at import into module-level constants and exported, they can be permanently no-op.
- qr-preserves-behavior (`src/config/tracing.js`): The added try/catch swallows all sdk.start() failures and only warns, so a genuinely broken SDK configuration silently produces no telemetry rather than surfacing at startup.
- qr-not-a-noop (`src/config/tracing.js`): The auth controller does `require('../config/tracing')` to obtain authOperations, but the meter/instruments are created at module load in tracing.js before sdk.start() is complete — since OTel-JS metrics have no proxy, getMeter() must be called after registration. However, sdk.start() runs synchronously at the top of the same module before the instruments are created, so registration precedes binding; this holds within a single module. The real risk is auth.controller.js and index.js require tracing.js, which does register — so binding is fine. Omit.
- qr-metric-naming (`src/config/tracing.js`): The new counter name 'http.server.request.outcomes' uses a plural noun for a plain count; semconv-style count metrics are typically singular unsuffixed (e.g. http.server.request rather than outcomes). Minor naming deviation.
