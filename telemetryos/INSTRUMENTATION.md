**Auto-fixed during review (2):**
- qr-unwired-telemetry (`src/index.js`): `app.use(httpMetricsMiddleware)` is registered in src/index.js AFTER `require('./app')` has already built the full Express stack (routes mounted at /v1, the 404 ApiError middleware and the error handler), so the metrics middleware sits at the very END of the stack and is never reached: matched routes end the response without calling next(), and unmatched requests are diverted into the 404/error handler. Neither http.server.request.duration nor http.server.request.outcomes will ever record, leaving both target SLIs without data.
- qr-export-pipeline (`src/config/tracing.js`): The PeriodicExportingMetricReader/OTLP exporters are never flushed: nothing calls `sdk.shutdown()`, and the process exit paths in src/index.js call `process.exit(1)` directly, so up to a full export interval of counter/histogram data (and buffered spans) is dropped on shutdown.
**Outstanding (1):**
- ⚠ general (`package.json`:80): The new pin `@opentelemetry/auto-instrumentations-node: ^0.57.0` predates the detected 0.200.0 / SDK-2.0 line used by `@opentelemetry/sdk-node@^0.200.0` and `@opentelemetry/sdk-metrics@^2.0.0`; the 0.57.x contrib bundle depends on `@opentelemetry/instrumentation@^0.57.x`, so yarn installs a second, older instrumentation core alongside the 0.200.0 one. — _Bump `@opentelemetry/auto-instrumentations-node` to the release aligned with core 0.200.0 / SDK 2.0 (e.g. ^0.58.0) so a single `@opentelemetry/instrumentation` version is resolved._
